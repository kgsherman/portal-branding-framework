Worked example

Aareal Bank in Section 1

Aareal's brand, taken from aareal-bank.com: a deep navy, a light sky blue for calls to action, warm cream and sand surfaces, four royal blues in the angled "light shards" of their artwork, square cards, and a slab-serif heading face over Helvetica. All of it maps onto existing tokens:

Outside Section 1 the example needed three things: the aareal-fonts CSS include (made with tools/embed_font.py), the white logo on the portal record, and the footer logo and address in the portal's footer settings. Building the example also turned up three framework fixes that every dark-header or light-CTA client now gets: header loading dots follow $ui-header-text, the knowledge banner text follows $ui-hero-text, and the onboarding modal's button hover derives from the CTA colour.

Quick start

New client in six steps

  1. Copy the template

    Open Service Portal › Themes › Business Portal Brand Template and use the related link Clone theme with includes. Rename the copy <Client> Theme before step 4, because the generated Next Experience theme takes the theme's name.

  2. Fill in Section 1 of CSS Variables, and nothing else

    • 1a paste the brand guide's colours under their own names: $acme-navy: #1B2A4A;
    • 1b assign every palette role (see palette roles)
    • 1c pin exact tints if the guide has them, otherwise shades are generated
    • 1d optional token overrides: CTA colour, headings, header, radii, font

  3. Set the logo on the portal record

    The Business Portal logo lives on Portals › Business Portal › Logo, not on the theme. A dark header needs a light logo.

  4. Click Sync Next Experience theme

    On the theme form. It regenerates the colours and font that Next Experience components read. Repeat after every palette or font change.

  5. Attach the theme to the portal

    Portals › Business Portal › Theme. If you created a new portal record instead of reusing business_portal, also create glide.service_portal.resize_text.<url_suffix>.base_font = 16. Without it, every size renders 60% too large.

  6. Verify

    Hard-refresh, check System Log for com.vaadin.sass errors, then walk the verification pages.

Architecture

How portal styling works

A Business Portal page pulls CSS from seven places. Five are compiled with the theme's variables; two are not. The framework covers all of them.

LayerCompiled with themeCovered by
Core sp-bootstrap-rem.scss: Bootstrap 3.4 + Service Portal core. Also turns ~150 variables into --now-* custom properties.yesSection 3 mapping
Theme CSS includes: the 15 Coral stylesheets, order 90–560yesSection 3 + overrides C2
Header and footer widgetsyesSection 3 + overrides B, C3
Widget CSS: compiled per widget, prefixed .v<sys_id>, injected after the theme CSSyeswidget knobs in Section 3 + overrides C4–C14 (selectors start with body to win)
portal-brand-tokens-overrides, order 1000yesitself
Next Experience theme block #sp_uxf_theme_variables: :root properties from the linked UX theme, loaded after the theme includesnooverrides A (html:root) + the Sync button
Static bundle css_includes_$sp.css: select2, date picker, slider, skeleton loadersneveroverrides C11
Section 1Palette ($palette-*) and token overrides
Section 2139 brand tokens ($ui-*), all !default
Section 3378 Bootstrap, Coral and widget variables
Override sheetReads tokens: bridge (A), footer and hero (B), fixes (C1–C14)
SyncReads tokens and writes the generated Next Experience theme

Why !default matters. The theme's variables are prepended to every compile. Section 2 declares each token with !default ("only if not set yet"), so whatever Section 1 sets wins, and everything derived from it (hover shades, header states, footer, banner) recalculates. It also means Section 1 can only reference $palette-*, its own 1a colours and literals, because the $ui-* tokens don't exist yet at that point.

Why a separate override sheet. About 240 OOTB rules ignore the theme. They use literal colours, spacing variables as radii, !important button radii, a static bundle that is never compiled, inline placeholder colours, and TinyMCE's own skin. Each fix is a small rule that reads tokens, so one shared copy serves every client. Each block names what it fixes, so it can be deleted once ServiceNow fixes the source.

Why the Sync button. The Product Catalog macroponent, AI Search, Now Assist and now-* components read ~5,000 component tokens from the Next Experience theme. ServiceNow resolves those into literal values when it writes the page, so overriding base --now-color--* scales in CSS isn't enough. Sync evaluates the theme's variables, rebuilds the ~40 base scales (brand, neutrals, alerts, focus, selection) and the font, and links <theme> (generated UX theme) to the portal theme.

$palette-neutral-60:   mix($aareal-darkblue, $aareal-sand, 58%);  // input borders
...
// --- 1d. Token overrides (optional) ----------------------------
$ui-button-primary-bg: $aareal-lightblue;  // sky blue call to action ...
$ui-button-primary-text: $aareal-darkblue; // ... with navy text
$ui-header-bg:         $aareal-darkblue;
$ui-header-text:       #FFFFFF;
$ui-radius-lg:         0px;                // square cards
Syntax rules. ServiceNow compiles with the Vaadin Sass compiler. One declaration per line, always ending in ;, with the ; before any // comment. No Sass maps. Colour functions (mix, darken, lighten, rgba($c, .5)) are fine. A parse error silently drops the whole stylesheet, and because these variables are prepended to every compile, a typo unstyles the entire portal. An undefined variable is written out literally and the browser ignores it, so that one thing quietly stays OOTB.

Upgrading the framework means replacing everything from SECTION 2 down with the new template and keeping Section 1.

Section 1b

Choosing palette roles

RoleDrivesRule of thumb
$palette-primaryPrimary buttons (white text), Actions menus, "Hide details" toggles, pagination, progress, carousel dots, active tab underline, banner tint≥ 4.5:1 against white
$palette-secondaryText links and text actions≥ 4.5:1 on white and on neutral-5
$palette-accentSelected state: active tab label, chosen items, active pills (white text)≥ 4.5:1 against white
$palette-focusFocus ring≥ 3:1 against white
$palette-neutral-5 … -1005 page background · 20 borders · 60 input borders · 85 muted text · 90 secondary text · 100 body textDarker at every step; 60 ≥ 3:1 on white; 85 ≥ 4.5:1 on 5
$palette-success / warning / danger / infoIcons, alert borders, required asterisks (danger), status buttonsDanger must read as "error"
…-lightAlert and label fills (text on them is neutral-100)Pale
  • Small brand guide? One colour can fill several roles. Aareal uses its navy for both primary and links, and borrows royal blues from its artwork for the selected state and focus.
  • CTA colour different from the brand colour? Keep $palette-primary on brand and set $ui-button-primary-bg in 1d, plus $ui-button-primary-text if the CTA is light. Aareal has sky-blue buttons with navy text on a navy brand.
  • No neutrals in the guide? Grade the brand's background colour into its darkest colour. Aareal goes from sand to navy: $palette-neutral-60: mix($aareal-darkblue, $aareal-sand, 58%);
  • Exact tints in the guide? Pin them in 1c. Generated shades are fixed mix() percentages with black or white (see 2a).
  • Dark header? Set $ui-header-bg and $ui-header-text in 1d. Hover, active and disabled states are derived from those two, and the footer follows unless you set $ui-footer-*. You'll need a light logo.

$ui-hero-bg accepts any CSS background (colour, gradient, url(…)). The default is a soft gradient built from the palette. Set $ui-hero-bg: null; and $ui-hero-text: null; to hand control back to the Portal Banner widget's own options.

Spacing (2g): $ui-space-3xs … -3xl (1–40px) feed ServiceNow's $sp-space--* scale and Bootstrap's padding variables. $ui-page-padding is the gap around page content and $ui-grid-gutter the space between columns. The override sheet never touches layout, so treat these as density controls and change them sparingly.

Section 2e

Fonts

$ui-font-family sets the font everywhere: body, Bootstrap, headings, the Coral includes (one hardcodes "Lato", fixed in C2), --now-font-family, and after Sync the Next Experience Typography style.

The font also has to be loaded. Stock Coral embeds Lato as base64 WOFF2 in the stylesheet portal-next-experience-lato-fonts (include order 100, ~736 KB). For a client font:

  1. Create an sp_css with @font-face rules for the weights you use (400, 600 or 700). python tools/embed_font.py "Family" 400=regular.woff2 700=bold.woff2 writes them with the WOFF2 embedded as base64, like the Lato sheet: self-contained and CSP-proof.
  2. Add it as a CSS include on the client theme with a low order, e.g. 95.
  3. Set $ui-font-family: "Client Sans", Arial, sans-serif; in 1d and click Sync.
  4. Remove the Lato include from the client theme if nothing uses Lato any more.

The Aareal example uses exactly this: the open-source slab Arvo (SIL OFL) stands in for Aareal's commercial ITC Lubalin Graph, embedded in the aareal-fonts include at order 95, with $ui-font-family-heading: "Arvo", Rockwell, Georgia, serif;. Never embed a commercial font without a web licence, and check the client's privacy and CSP rules before hot-linking a font CDN instead.

Keeping it working

Maintenance and upgrades

Framework upgrade. Replace Sections 2–4 of each client theme, keep Section 1. Replace the shared override sheet and PortalBrandTokensUx. Sync each theme.

After a ServiceNow upgrade, or when adding widgets, rerun the two audits on a lab portal:

  • Regression diff. Compile core with stock Coral and with the template and compare declaration by declaration. The endpoint compiles any theme: /styles/scss/sp-bootstrap-rem.scss?portal_id=…&theme_id=…&uxf_theme_id=…. Expect the same declaration count and only the known intentional differences.
  • Loud-palette sweep. Put an obviously fake palette in the lab theme's Section 1 (sepia-tinted neutrals, magenta, purple and green brand colours), Sync, walk the verification pages. Anything still Coral teal, blue or grey is hardcoded. Find its source and add a fix.

Adding a fix: put it in the matching C-section, start the selector with body, use tokens only, never change layout, and name the widget or stylesheet in a comment.

Adding a token: declare it in Section 2 with !default and a comment, map platform variables to it in Section 3, add it to the reference, and to PortalBrandTokensUx.buildBaseColours() if Next Experience components should follow it.

Update sets

Deployment

Framework, once per instance (update set Portal Brand Tokens - Framework): the portal-brand-tokens-overrides stylesheet and include, the PortalBrandTokensUx script include, the two UI actions on sp_theme, and the Business Portal Brand Template theme with its 15 include records.

Per client: the client theme and its include records (made by the clone), the portal's theme and logo, the base_font property if it's a new portal record, and the generated UX theme. Either move the generated sys_ux_theme, sys_ux_style and m2m_theme_style records, or click Sync once in the target instance after committing.

Aareal example: update set Portal Brand Tokens - Aareal Bank example (theme, its includes, aareal-fonts, generated UX theme). It depends on the Framework set. The lab portal's logo and footer settings stay in the scratch set.

Use the UI actions in your own session so changes land in your current update set. Scripts that run as system (scheduled jobs, triggers) write to Default; move those records afterwards.
